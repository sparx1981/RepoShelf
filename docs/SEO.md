# Search engine discovery

`npm run build` generates a public `/explore.html` directory, paginated category pages, and individual project pages with HTML descriptions, author README excerpts where available, technologies, licences, demo-check dates, and related project links. Project pages also quote saved author-documented purpose, audience and account/API-key/paid-service/hosting requirements. Missing requirements are explicitly unknown. Recorded source-update and release dates are shown without claiming ongoing maintenance. Category introductions explain relevant comparison criteria. They work without JavaScript. Project actions return to the existing storefront and sign-in flow.

The build uses the moderated browse index and the same `publishedEligible` check as public browsing. Hidden, excluded, pending, quarantined, unavailable, and stale listings are omitted. Each build removes the previous generated project/category directories before writing current pages. Verified GitHub renames receive a direct HTTP 301 to the current published page, including its Markdown alternative. Rename proof comes from a matching immutable GitHub repository ID or an observed GitHub API redirect. Unknown renames, reused names and unpublished destinations return 404. The redirect fallback uses the existing editorial function; it does not require an extra serverless function or a paid bulk-redirect plan.

Generation is bounded to 5,000 project pages to limit build time and deployment size. Previously selected pages remain selected while they still pass publication checks. Remaining slots reserve up to 12 eligible projects per category before filling by the existing source-aware popularity ranking. At capacity, stability takes priority over replacing an existing eligible page with a newly popular listing. `data/seo-registry.json` stores selection and proven rename history; normal catalogue publication persists it alongside the saved data. This starts with the first publication using the registry and cannot recover unknown historic renames. Only selected projects receive public pages and sitemap entries; others continue to work through the existing storefront. Categories contain up to 48 links per page with ordinary previous/next anchors. Empty categories are omitted. The storefront links to the directory, and its share action uses a public page when that listing is present in the generated manifest, falling back to the existing `?project=` link otherwise.

Every public page has a unique title and description, an absolute canonical URL, Open Graph/Twitter metadata, and a social image. Project screenshots are used where available; a generated 1200×630 RepoShelf PNG is the fallback. JSON-LD describes the website, category collections, source-code projects, and breadcrumbs. Stars and forks are not presented as review ratings. Sitemap entries omit `lastmod` rather than presenting build time or unrelated repository updates as page modification dates.

The canonical origin defaults to **https://www.reposhelf.co.uk**, matching the application's existing account configuration. To deploy under another domain, set `REPOSHELF_SITE_URL` to its HTTPS origin before building. This is a public build setting, not a secret, and is independent of OAuth's allowed origins. Do not set it to a temporary preview URL. The build rejects origins containing credentials, paths, queries, or fragments.

When `VERCEL_ENV` is `preview` or `development`, HTML receives `noindex, nofollow`, the sitemap has no entries, and robots disallows crawling. Production account, administration, legal-acceptance, and offline pages also receive `noindex`. API responses have an `X-Robots-Tag` header. Public legal policy pages have canonical URLs but are excluded from the discovery sitemap. `/index.html` permanently redirects to `/`.

After merging and deploying:

1. Verify `/robots.txt`, `/sitemap.xml`, `/explore.html`, and a linked project URL on the production domain.
2. Add the canonical domain to Google Search Console and Bing Webmaster Tools using an account you control. Complete their domain-verification process and submit `/sitemap.xml`.
3. Use URL Inspection to request crawling of the home page and directory, and monitor indexing and search queries. Publishing a sitemap enables discovery; search engines decide whether and when to index pages.

No account verification, sitemap submission, or production deployment is performed by the build. `npm run test:seo` checks generated HTML, pagination, moderation, escaping, canonical configuration, sitemap consistency, repeated builds, retirement, and preview exclusions without calling external services.

## Agents and LLMs

`/llms.txt` points to `/agent-guide.html.md`, `/explore.html.md`, and `/discovery.json`. The public project and category pages advertise Markdown alternatives through `rel="alternate" type="text/markdown"`; all public HTML advertises the discovery guide with `rel="describedby"` and the OpenAPI schema with `rel="service-desc"`. The home page identifies the source repository in its website metadata, and the agent guide describes the public catalogue with DataCatalog/Dataset structured data.

Markdown alternatives append `.md` to the canonical HTML path. They contain project descriptions, author excerpts where present, source links, declared licences, and recorded check dates. Author text is escaped as content. JSON chunks contain only a small whitelist of public metadata fields; full catalogue records, account data and credentials are not copied into them.

The discovery manifest reports coverage explicitly: at most 5,000 published listings, not the full catalogue. Follow `firstPage`, then each chunk’s `next` URL. Chunks contain at most 25 records and are also split to stay below 64 KiB. They share a version derived from their content. JSON includes compact author context, unknown requirement kinds and maintenance dates. A rebuild removes old chunks; a reader receiving 404 for an older version should re-fetch the manifest and restart. Metadata names observation dates separately from generation time.

Markdown and JSON responses receive `X-Robots-Tag: noindex` to keep machine-readable copies out of search results; their corresponding canonical HTML pages remain indexable. The existing production wildcard robots policy already allows public search and assistant crawlers. No crawler-specific rule overrides that policy, and private REST/MCP endpoints keep their existing authentication. Preview deployments remain excluded from crawling.

`llms.txt` is an optional discovery convention, not a ranking requirement. Google’s [AI features guidance](https://developers.google.com/search/docs/appearance/ai-features) says ordinary SEO fundamentals and accessible, useful content apply. The [llms.txt proposal](https://llmstxt.org/) recommends concise guides, linked Markdown pages, and standard link relations. Neither guarantees that a search engine or model will index or cite a website.

## Performance and repeatable checks

Saved demo screenshots used on public project pages receive 480 px and 960 px WebP alternatives, with a JPEG fallback and explicit dimensions. The build never enlarges images and only processes already saved demo captures. Nested project/category pages also use the existing minified, fingerprinted CSS assets. `artifacts/seo-build.json` records aggregate original/mobile/desktop image bytes and missing originals. Missing or undecodable originals keep the existing fallback.

`node scripts/verify-discovery-ui.mjs` runs a controlled current-evidence catalogue through an actual HTTP agent journey and Chromium. It checks category pagination, project evidence and canonical citations, HTTP 301s, responsive WebP selection, keyboard navigation and reading with JavaScript disabled. CI saves mobile/desktop screenshots and lab LCP/CLS samples in `discovery-performance.json`. These are fixture lab measurements; they are not production field Core Web Vitals, and INP is not measured. Existing MCP/client/key tests continue to exercise the authenticated connector separately.

Use the production audit command and the owner’s Search Console Core Web Vitals reports or PageSpeed Insights for real traffic performance. The implementation does not invent field measurements or an agent-readiness score. Account verification and sitemap submission steps are in [INDEXING_SETUP.md](INDEXING_SETUP.md).
